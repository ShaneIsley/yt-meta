# yt-meta — Repo Review

**Date:** 2026-07-05
**Scope:** Whole repo at `main` (v0.7.1). Four parallel reviewers: prior-findings audit (vs the 2026-06-02 ultra-review), fresh correctness, architecture/code quality, usability/DX → synthesis. Offline suite: 264 passed, 0 failed. `ruff check`: clean.

## Executive summary

The June review's roadmap was executed thoroughly — and it shows. **16 of 17 High findings and 15 of 23 Mediums are verifiably fixed** (7 more partially), including every release blocker: the facade is a real context manager, the pickle-RCE cache is now JSON+WAL with a legacy-refusal guard, the date-filter DSL is unified, packaging is clean, the README's fabricated APIs are gone, and the offline test suite is fast and well-marked. The codebase at v0.7.1 is structurally healthy.

The new debt is concentrated in three places:

1. **A key-vocabulary split between the filter layer, the parser, and the docs** — three documented comment-filter keys (`channel_id`, `is_by_owner`, `is_hearted_by_owner`) can never match because the parser emits `author_channel_id`, `is_creator`, `is_hearted`; missing-key ⇒ reject means these filters silently yield **zero comments**. `is_hearted`/`is_pinned` are additionally hardcoded `False`, so two shipped examples (26, 28) demonstrate nothing. Confirmed independently by three reviewers.
2. **Retry/error handling is only half-wired.** `_retry.py` is good but protects only continuation POSTs; all six page GETs are unretried. Worse, those GETs catch `httpx.RequestError`, which does **not** cover `raise_for_status()`'s `HTTPStatusError` — so a single transient 429/5xx on one video's watch page during `fetch_full_metadata=True` kills the whole channel/playlist generator with an unwrapped exception, exactly the failure the retry module was built for.
3. **The README's caching section states the opposite of the code** (claims in-memory caching by default; default is `DummyCache` = no caching), and the persistent cache round-trips `publish_date` from `datetime` to string — the M4 type-drift bug reintroduced for `cache_path` users.

## High-severity findings

### C1 — Comment filter keys can never match; filters silently drop everything
`filtering.py:39-49` advertises `is_by_owner`, `is_hearted_by_owner`, `channel_id`; `comment_parser.py:521-540` emits `is_creator`, `is_hearted`, `author_channel_id`. `apply_comment_filters` (`filtering.py:333-335`) treats a missing key as fail → `filters={"channel_id": {"eq": ...}}` rejects 100% of comments, no error. Tests pass because they filter synthetic dicts that already contain the doc-side keys (`tests/test_comment_fetcher.py:492-500`). Additionally `is_hearted` and `is_pinned` are hardcoded `False` on the production path (`comment_parser.py:532,534`), so examples 26 and 28 are dead demos.
**Fix:** map filter keys → parser keys (or rename parser output), populate `is_hearted`/`is_pinned` from toolbar/thread state, and add a schema test asserting every `COMMENT_FILTER_KEYS`/`FAST_VIDEO_FILTER` key exists in the corresponding parser's real output. (Same class: `description_snippet` is a FAST filter but `parse_lockup_view_model` never emits it — `parsing.py:435-445`.)

### C2 — HTTP 4xx/5xx escape the `except httpx.RequestError` guards
`fetchers.py:248-255, 315-324, 395-404, 430-439, 764-771`. `httpx.HTTPStatusError` is not a subclass of `RequestError`, so a 404/429/500 escapes unwrapped. `get_video_metadata`'s docstring promises `VideoUnavailableError` for "404, rate-limit" — false. During hydration, `_process_videos` (`fetchers.py:89`) catches only `VideoUnavailableError`/`MetadataParsingError`, so one 429 kills the whole iteration mid-stream. The comment path gets it right (`comment_api_client.py:107` catches `httpx.HTTPError`).
**Fix:** catch `httpx.HTTPError` at all five sites.

### C3 — Retry wired only on continuation POSTs (H9 remainder)
`request_with_retries` wraps `fetchers.py:182` and `comment_api_client.py:347/437` only. Unretried: watch page (`fetchers.py:248` — once **per video** when hydrating), channel/shorts/streams pages (`:397/:431/:316`), playlist page (`:765`), comment initial page (`comment_api_client.py:104`).
**Fix:** route all six GETs through `request_with_retries`. Pairs naturally with C2.

### C4 — `limit=-1` comment fetch yields zero comments
`client.py:417/465` + `comment_fetcher.py:135,158`. Docstring says "Pass None or -1 for unbounded"; with `-1`, the loop condition `comment_count < limit` is `0 < -1` → no request ever issued; empty generator, no error. `limit=None` works.
**Fix:** normalize `limit < 0 → None` in `CommentFetcher.get_comments`.

### C5 — Selective comment filters trigger silent truncation
`comment_fetcher.py:156-198`. `found_comments` counts post-filter survivors; three consecutive pages with zero *passing* comments trips `EMPTY_PAGE_LIMIT`. `filters={"author": {"eq": "X"}}` on a busy video stops after ~3 pages and misses deeper matches — contradicting the docstring ("filters do NOT reduce request count").
**Fix:** base the empty-page counter on new unique comment IDs seen (pre-filter).

### C6 — README caching section is false
`README.md` §Caching (~252-264) claims "By default, YtMeta uses a simple in-memory dictionary… second call will be instant." Code: default is `DummyCache` (stores nothing, `caching.py:19-42`). The README's own API reference (line ~455) says the opposite, correctly. Users trusting this will hammer YouTube in loops. Same false claim in `examples/features/19`.
**Fix:** rewrite section: "caching disabled by default; pass `cache={}` for in-memory or `cache_path=` for persistent."

### C7 — Past live streams get `publish_date=None`
`parsing.py:387,429-433`. Completed streams render "Streamed 2 days ago"; the `"ago"` probe matches but `dateparser.parse("Streamed 2 days ago")` returns `None` (verified). Every past stream has `publish_date=None`; any date filter drops all of them. The fixture only contains *scheduled* items, so tests never see it.
**Fix:** strip a leading `Streamed ` prefix before parsing; add a completed-stream fixture.

### C8 — `datetime` passed as `start_date` raises `TypeError` mid-pagination
`filtering.py:235-238` normalizes only `str`; a `datetime` reaches `video_publish_date.date() < final_start_date` (`fetchers.py:541-545`) → `TypeError` (date vs datetime). The last remaining crash on a documented input shape.
**Fix:** one-line normalize (`.date()` on datetime) in `build_date_filter`.

## Medium-severity findings

- **M-a — SQLite cache round-trip changes `publish_date` type.** `caching.py:112` uses `json.dumps(..., default=str)`; cache hit returns a string where a fresh call returns `datetime` — M4 reintroduced for `cache_path` users, and injected-dict caches behave differently again. Fix: explicit ISO encode/decode (revive on read) or normalize the field to ISO everywhere and document it. (3 reviewers independently.)
- **M-b — `_apply_status_tracking` loses preserved content on the 2nd consecutive "unavailable".** `fetchers.py:44-50` preserves only when `prior_status == "ok"`; ok→unavailable→unavailable (force_refresh) nulls title/counts, violating "prior data is never lost". Fix: preserve whenever `status != "ok" and prior`.
- **M-c — Reply pagination likely stops after page 1.** `extract_continuation_token` (`comment_api_client.py:356-410`) handles only `continuationEndpoint.continuationCommand`; reply threads commonly use the `button.buttonRenderer.command.continuationCommand` form. Unverifiable offline (fixture is synthetic, live contract fetches limit=2). Fix: also check the button path; add a live contract assertion on a >50-reply thread.
- **M-d — Inner `except Exception: break` still truncates silently (M23 remainder).** `comment_fetcher.py:205-207, 298-300`; `get_comment_replies` still wraps bare `Exception` as `VideoUnavailableError` (`:304-308`); `TranscriptFetcher.get_transcript` returns `[]` on *any* exception (`transcript_fetcher.py:35-37`) — "no transcript" indistinguishable from a bug or rate-limit. Fix: narrow to httpx errors, re-raise the rest.
- **M-e — Playlist `publish_date` classified FAST contradicts docs and silently drops.** Playlists use `content_type="videos"` (`fetchers.py:840-843`) so `publish_date` is a fast filter; items lacking it are dropped with no full-metadata fetch, while README (~331, 427-428) and the docstring promise slow-path hydration. Fix: playlist-specific content_type excluding `publish_date` from the fast set.
- **M-f — Comment subsystem: resources shared, code still siloed (M1 remainder).** `CommentAPIClient` re-implements ytcfg/ytInitialData extraction with weaker regexes (`comment_api_client.py:119-143` — no `window["ytInitialData"]` form → comments can silently die while metadata works) and caches under `video_initial:` while `VideoFetcher` uses `video_meta:` — mixed workflows fetch every watch page twice. Fix: one shared `get_watch_page_data(video_id)`; reuse `parsing.YT_INITIAL_DATA_RE`.
- **M-g — Input `ValueError`s escape the documented `YtMetaError` umbrella.** `utils.py:33-41,116-140` raise builtin `ValueError`; README §Error Handling doesn't mention it. Scheme-less URLs produce the confusing "hostname '' is not a known YouTube domain". Fix: document, and special-case the missing-scheme message.
- **M-h — Datetime/key inconsistency across return shapes.** Within one video dict: `publish_date` datetime, `upload_date` raw string, `scheduled_start_time`/`status_*` ISO strings; comments use `id`, videos `video_id`. Undocumented. Fix: document now; normalize in the next minor.

## Low / polish

- `Retry-After` honored without cap (`_retry.py:89-92`) — apply `max_delay`.
- `build_date_filter` coarsens `gt`/`lt` to `gte`/`lte` and discards an `eq` publish_date condition when start/end kwargs also given (`filtering.py:228-246`).
- `max_videos=0` yields 1 item (`fetchers.py:98-103`).
- `get_video_comments` is a generator, so its documented `ValueError` guards fire on first `next()`, not at call time (`client.py:388-434`) — eager-validate, return inner generator.
- `get_channel_shorts` still lacks `start_date`/`end_date` kwargs (`client.py:317`).
- `BestCommentFetcher` alias still has no `DeprecationWarning` (`comment_fetcher.py:312`).
- Dead code ~500+ LOC: `constants.py` (entire, zero imports), ~half of `CommentParser` (`comment_parser.py:19-401`), `utils.parse_vote_count`, legacy `parsing.extract_videos_from_*` kept alive only by tests, `parse_playlist_metadata` unreachable from the facade (wire up a `get_playlist_metadata` or drop it), dead `stop_pagination` (`fetchers.py:591,604`), dead `if not continuation_data: break` ×4, dead test fixtures patching `requests.Session` (`test_client.py:15-31`).
- Facade duplication: `_get_channel_{page,shorts,streams}_page_data` are three verbatim copies (`fetchers.py:308-453`); `get_video_comments` vs `get_video_comments_with_reply_tokens` near-identical (`client.py:388-481`).
- Typing: no `py.typed` (annotations invisible to consumers' IDEs); fetcher entrypoints unannotated (`fetchers.py:616-626, 663-671, 701-709, 810-819`); `languages: list[str] = None` mistyped default (`client.py:208`).
- pyproject: `[tool.ruff]` placeholder comment still present (~:60-62); classifiers/URLs thin; dev deps split across `[project.optional-dependencies].dev` and `[dependency-groups].dev` inconsistently.
- Examples: 26 & 28 dead (see C1); 05 prints a key the lockup parser never emits; 19 says "SqliteDict" and repeats the false in-memory claim; 31 imports `tqdm` (dev-only); 30/32 cosmetic bugs.
- README gaps: no context-manager/`close()` docs, no `get_video_transcript`/`get_channel_shorts` API-reference entries, `clear_cache(prefix=)` undocumented, and — most notably for this project — **no "YouTube renderer migrations break this library" section** telling users how to recognize drift, run `pytest -m contract`/`make drift`, and report. The retry/backoff behavior is also worth advertising.
